1. What a node is, and what a validator is1. ノードとは何か、バリデータとは何か

In this protocol, a post does not go straight from a phone to a blockchain. A user signs an action with their wallet — that signature is the proof of authorship — and the signed action is handed to a node: a server program that is always on. A node does two jobs. このプロトコルでは、投稿はスマホから直接ブロックチェーンへ行くわけではありません。利用者は自分のウォレットで投稿に署名し（その署名が「本人が書いた」証明になります）、署名済みの投稿をノード（常時動いているサーバープログラム）に渡します。ノードの仕事は2つです。

Reading — every node読み取り — すべてのノード

The node watches the chains (name NFTs on Ethereum, actions on Base), keeps its own indexed copy, and answers the app's and the web viewer's questions: timelines, profiles, notifications. This job needs no keys and no funds at all. If a node lies or goes quiet, users can simply ask another node — the signed actions and the chain remain the source of truth. ノードはチェーン（Ethereum の名前 NFT、Base の投稿）を監視して自分用の索引を持ち、アプリや Web 版からの問い合わせ（タイムライン、プロフィール、通知）に答えます。この仕事には鍵も資金も一切いりません。あるノードが嘘をついたり止まったりしても、利用者は別のノードに聞けばよく、署名済みの投稿とチェーン自体が正本であり続けます。

Delivering — a node with a validator wallet届ける — バリデータウォレットを持つノード

A node whose operator has added a validator wallet also takes the signed actions waiting in its queue and submits them to the CawActions contract on Base, paying the gas itself. The contract verifies each signature before accepting anything, so a validator cannot forge or alter a post — it can only deliver, delay, or decline. For each delivered action, the poster's tip (CAW) is credited to the validator's own CAW name. 運営者がバリデータウォレットを追加したノードは、待ち行列にある署名済みの投稿を Base の CawActions コントラクトへ提出し、ガス代を立て替えます。コントラクトは受け付ける前に各署名を検証するので、バリデータは投稿を偽造・改ざんできません。できるのは届ける・遅らせる・断る、だけです。届けた投稿ごとに、投稿者のチップ（CAW）がバリデータ自身の CAW 名義に入ります。

Nobody's permission is needed to run either kind. There is no application, no allow-list, no official status to apply for: you install the software, and you are a node. Every additional node means the network keeps working even if any single server — including the first one — stops. どちらの役割も、誰の許可もいりません。申請も、許可リストも、「公式」の認定もありません。ソフトを入れれば、その時点であなたはノードです。ノードが1台増えるごとに、最初の1台を含め、どのサーバーが1台止まっても全体が動き続けるようになります。

2. What you need, and what it honestly costs2. 必要なものと、費用の実態

No sugar-coating: running a node costs a little money every month, and at today's prices the tips do not pay it back. People run nodes so that their own access never depends on a stranger's server staying up, and so the network is harder to stop — not because it is profitable. Here are the real numbers, measured on the first public node in November 2026. Prices, gas and the CAW price all move, so treat every figure as a dated example, not a promise. 率直に言います。ノード運営には毎月少しお金がかかり、現状の価格ではチップで元は取れません。ノードを立てる理由は、儲かるからではなく、自分の利用が他人のサーバーの都合に左右されなくなることと、全体が止まりにくくなることです。以下は2026年11月に最初の公開ノードで実測した数字です。料金・ガス・CAW 価格は変動するので、どの数字も「その時点の実例」として読んでください（約束ではありません）。

It is safe to re-run: kit-managed files are refreshed, and if you have changed anything else in the source tree yourself, it stops and asks you to review instead of overwriting your work. Read red lesson #2 before you conclude your password is wrong. この手順で事業者のシリアルコンソールからログインする作業には、特有の罠があります — 静かにタイムアウトするログインプロンプトと、止まっていないのに表示だけ消えるスマホ画面です。パスワードが間違っていると結論する前に、赤い教訓 #2 を読んでください。

To check liveness, ask the API — https://<your-node-url>/api/instances should answer with JSON naming network id 1. (Checking the root path / tells you nothing: red lesson #3.) Then just wait: the first chain sync takes a while on public RPCs. ステップ3 — 生きているか確認する。公開 URL は /opt/caw/node-url.txt に書かれます。ノードは公開ノード一覧へ自動で知らせるので、アプリは勝手に見つけます。死活確認は API に聞いてください — https://<あなたのノードURL>/api/instances が、ネットワーク ID 1 を含む JSON を返せば正常です（ルート / を見ても何も分かりません：赤い教訓 #3）。あとは待つだけです。初回のチェーン同期は、公開 RPC 経由だと時間がかかります。

The installer deliberately ships with an empty validator key, so at this point your node can read and serve but cannot deliver a single post. This step is not optional if you want delivery. Download make-validator-wallet.sh from the same node kit and run it on your server as root, with your CAW name's number: ステップ4 — 届けるなら必須：バリデータウォレットを作る。インストーラーは意図的にバリデータの鍵を空で出荷します。この時点のノードは、読む・届ける先に渡すことはできても、投稿を1件もチェーンに届けられません。届ける役をするなら、この手順は省略できません。同じノードキットの make-validator-wallet.sh をサーバー上で root 実行してください（引数は自分の CAW 名義の番号）： 
    bash make-validator-wallet.sh <your CAW name number>
    The wallet is generated on your server; the private key is written straight into the node's .env file and is never printed, never sent anywhere. The script prints only the public address. Send that address a small amount of ETH on Base (about 0.005 ETH is plenty), then restart the node: ウォレットはあなたのサーバー上で生成され、秘密鍵はノードの .env に直接書かれます。画面に出ることも、どこかへ送られることもありません。表示されるのは公開アドレスだけです。そのアドレスへ、Base 上の ETH を少額（0.005 ETH 程度で十分）送ってから、ノードを再起動してください： 
    systemctl restart caw-node
  • Step 5 — Optional: subsidy mode. The upstream software checks each action's tip against its delivery cost and declines actions whose tip is too small — at today's prices, that is almost all of them. If you want your node to actually deliver, re-run the installer with CAW_NODE_SUBSIDY=1: that one check is switched off on your node only, and you carry the ~¥0.36 per post yourself. Posters still pay exactly what the contracts require; nothing about other nodes changes. The first public node runs this way, openly. ステップ5 — 任意：補助モード。原典のソフトは、投稿ごとにチップと配送実費を比べて、足りない投稿を断ります。現状の価格では、それはほぼ全ての投稿です。本当に届ける役をするなら、CAW_NODE_SUBSIDY=1 を付けてインストーラーを再実行してください。そのチェックが自分のノードでのみ外れ、1件約0.36円を自分で被ります。投稿者が払う額はコントラクトの定め通りで変わらず、他人のノードにも影響しません。最初の公開ノードは、この形で公表して動いています。

4. Keeping it healthy: caw-doctor4. 健康を保つ：caw-doctor

The installer also places a small operations tool on your server: caw-doctor. It runs entirely on your own machine — your node's local API, your own database, and read-only checks against a public Base RPC. There is no central server and nothing phones home. Four subcommands: インストーラーは、小さな運用ツール caw-doctor もサーバーに置きます。すべて自分のサーバー内で動きます（自分のノードのローカル API、自分のデータベース、公開 Base RPC への読み取り確認のみ）。中央サーバーはなく、どこへも送信しません。サブコマンドは4つです：

caw-doctor status

A read-only overview: is the service up, does the API answer, what network does it report, how many queue rows sit in each state (pending / processing / done / failed), how old the oldest stuck-looking row is, how much Base ETH the validator wallet holds, and which cawonce the chain expects next for your name. Start here whenever something feels off. 読み取り専用の現状一覧です：サービスは上がっているか、API は応答するか、ネットワーク ID は何か、待ち行列の件数（pending／processing／done／failed）、詰まっていそうな行の古さ、バリデータウォレットの Base ETH 残高、チェーンが次に期待している cawonce。何かおかしいと感じたら、まずこれです。

caw-doctor check

The cron-friendly version. Silent success: exit code 0 means healthy. It exits non-zero and prints one line per problem when the API is down, when a row has sat in processing for over 15 minutes (the known stall signature), when any failed rows exist, or when the validator balance falls below 0.0005 ETH (warning) or 0.0001 ETH (critical). An hourly cron entry is enough: cron 向けの形です。正常なら終了コード 0。API が落ちている、行が processing のまま15分を超えた（既知の詰まりの兆候）、failed 行がある、残高が 0.0005 ETH 未満（警告）／0.0001 ETH 未満（危険）——のいずれかで、問題ごとに1行出して非ゼロで終わります。1時間に1回の cron で十分です： 

17 * * * * root /usr/local/bin/caw-doctor check >> /var/log/caw-doctor.log 2>&1

caw-doctor restart

Restarts the node service and waits until the API answers again. This is the documented first move when a post stops moving: a row wedged in processing is normally resumed by a restart. It asks for confirmation unless you pass --yes. ノードを再起動し、API が応答を返すまで待つコマンドです。投稿が止まったときの「まずやること」がこれで、processing で固まった行は再起動で処理が再開するのが通常です。--yes を付けない限り、実行前に確認します。

caw-doctor unblock

Releases failed queue rows that are blocking new posts. Why this exists: when a signed action fails, its row stays in the queue marked failed — and the node refuses any new action that reuses that row's cawonce (a per-sender sequence number), so one bad row can quietly block a poster's later posts. Deleting database rows by hand is risky, so unblock checks the chain first, for every failed row: it reads the sender's on-chain nextCawonce and offers deletion only when the row's cawonce is provably dead — either it never landed (the chain still expects exactly that number, so freeing it is safe) or it was already consumed on-chain (the row is a ghost). If the chain says anything else, or cannot be read, the row is left untouched. It never touches pending or processing rows, asks before each deletion, and prints exactly what it removed. failed 行が新しい投稿を塞いでいる状態を解くコマンドです。なぜ要るか：署名済みの投稿が失敗すると、その行は failed として待ち行列に残り、ノードはその行の cawonce（送信者ごとの通し番号）を再利用する新しい投稿を拒否します。つまり悪い行1つで、その人の後の投稿が静かに止まります。データベースの行を手で消すのは危ないので、unblock はまずチェーンを確認します：送信者のオンチェーン nextCawonce を読み、その行の cawonce が「死んでいる」と証明できる場合だけ削除を提案します — 具体的には、チェーンに一度も載っていない（チェーンがまさにその番号を待っているので、解放しても安全）か、既にチェーン上で消費済み（その行は亡霊）の場合です。それ以外の答え、またはチェーンが読めない場合は、その行には触りません。pending／processing の行には決して触らず、削除ごとに確認し、消したものを正確に表示します。

The two delivery problems you will actually meet. (1) The stall: the validator delivers one post after a restart, then wedges again on the next — a queue row sits in processing forever. Restart first (caw-doctor restart); that has resumed every stall seen so far. (2) The blockage: posts from one name start failing with a cawonce collision even though the chain is fine — a leftover failed row is holding the number. That is what unblock is for. Both patterns, and the manual recovery they were learned from, are written up in the red lessons below. 実際に出会う2つの配送トラブル。（1）詰まり：再起動後は1件届くのに、次でまた止まる — 待ち行列の行が processing のまま固まります。まず再起動（caw-doctor restart）。これまで見た詰まりは、すべてこれで再開しました。（2）塞ぎ：チェーンは正常なのに、ある名前からの投稿が cawonce の衝突で失敗し続ける — 残っていた failed 行が番号を握っています。これが unblock の出番です。どちらの型も、それを学んだ手作業の復旧も、下の赤い教訓に書いてあります。

5. Day-to-day operations5. 日常運用

  • When a post stops being delivered, restart first. systemctl restart caw-node (or caw-doctor restart). Do this before touching the database or the logs — in practice it clears the common case. (Red lesson #6.)投稿が届かなくなったら、まず再起動。systemctl restart caw-node（または caw-doctor restart）。データベースやログに触る前にこれをやってください。実際、よくあるケースはこれで解けます。（赤い教訓 #6）
  • Logs. Live: journalctl -u caw-node -f. Recent history: journalctl -u caw-node --no-pager -n 80. The tunnel has its own unit, caw-tunnel.ログ。リアルタイムは journalctl -u caw-node -f、直近は journalctl -u caw-node --no-pager -n 80。トンネルは別ユニット caw-tunnel です。
  • Queue state. caw-doctor status summarises it; for the raw rows, the beginner guide in the node kit shows the exact database query.待ち行列の状態。caw-doctor status が要約します。生の行を見たい場合のデータベースへの問い合わせは、ノードキットの初心者向けガイドに正確な文があります。
  • Balance. Keep an eye on the validator wallet (caw-doctor check warns you). Top up with small amounts only — the wallet is gas money, nothing else.残高。バリデータウォレットを見ておいてください（caw-doctor check が警告します）。補充は少額だけ。このウォレットはガス代専用です。
  • Updating. Re-run the installer (the same one-liner). It refreshes what the kit manages — including caw-doctor itself — re-checks the pinned source commit, and stops for your review rather than overwriting anything else you changed. Read the release notes of the node kit before updating a node that is delivering well; there is no auto-update, deliberately.更新。インストーラーを再実行します（同じ1行）。キットが管理するもの（caw-doctor 自身を含む）は更新され、固定コミットの照合もやり直します。自分で変えた他の部分は、上書きせずに止まって確認を求めます。順調に届けているノードを更新する前に、ノードキットの変更点に目を通してください。自動更新はありません（意図的にです）。
  • Your public URL can change. The free Cloudflare quick tunnel gives a new address when it restarts. Your node re-announces the new address to the registry automatically (every 6 hours and at boot), and the current one is always in /opt/caw/node-url.txt — but anything you hard-coded with the old address will point at a dead tunnel. (Red lesson #5.)公開 URL は変わり得ます。無料の Cloudflare クイックトンネルは、再起動すると新しいアドレスになります。ノードは新しいアドレスを一覧へ自動で知らせ直し（起動時と6時間ごと）、現行のものは常に /opt/caw/node-url.txt にあります。ただし古いアドレスをどこかに固定で書いていたら、そこは死んだトンネルを指し続けます。（赤い教訓 #5）
  • Keep the server itself patched. Apply Ubuntu security updates regularly (apt update && apt upgrade), and reboot the VPS occasionally — the node services come back on their own.サーバー自体の更新も。Ubuntu のセキュリティ更新は定期的に（apt update && apt upgrade）。たまに VPS を再起動しても、ノードのサービスは自動で戻ります。

6. Security, briefly and plainly6. セキュリティ — 短く、正直に

  • The validator key lives in exactly one place: the .env file inside your server's node directory. It was generated there and it should never leave. Never paste it into a chat, a ticket, an issue, a screenshot, or a video call — anyone who has it owns the wallet. Nobody from this project will ever ask you for it; there is no support process that needs it.バリデータの鍵の居場所は1つだけ：あなたのサーバーのノード用フォルダ内の .env です。そこで生まれて、出ていく理由がありません。チャット、問い合わせ、Issue、スクリーンショット、ビデオ通話 — どこにも貼らないでください。持った人がウォレットの主になります。このプロジェクトの誰かがあなたの鍵を聞くことは決してありませんし、鍵が要る支援手順も存在しません。
  • Keep the wallet poor. It is a gas-only wallet. If the server is lost or compromised, whatever ETH sits in it is gone — another reason to top up little and often instead of parking a large amount.ウォレットは貧乏に保つ。ガス代専用です。サーバーを失ったり侵害されたりすれば、中の ETH は戻りません。まとめて置かず、少額をその都度補充する理由がこれです。
  • Record the root password. Yes, again — it is the single most expensive mistake on this page. See red lesson #1.root パスワードは記録する。はい、もう一度言います。このページで一番高くついた失敗です。赤い教訓 #1 を見てください。
  • SSH hygiene. Once you are set up, prefer key-based login and consider turning password login off; keep the firewall as the installer leaves it (SSH only — the API itself stays on localhost behind the tunnel); and treat the database password file /root/.caw-db-pass with the same care as any other credential on the box.SSH の基本。設定が済んだら、鍵ログインを優先し、パスワードログインを切ることも検討してください。ファイアウォールはインストーラーのまま（SSH のみ — API 自体はトンネルの後ろで localhost のまま）に。データベースのパスワードファイル /root/.caw-db-pass も、そのサーバー上の他の資格情報と同じ扱いで。

Where the author of this page actually got stuckこのページの作者が実際に詰まったところ

Everything in this section is red because it deserves to be. These are not generic warnings copied from a checklist — each one actually happened to me while I was setting up the first public node on November 12, 2026, and each one cost me real time. They are written the way I wish someone had written them for me. この節が全部赤いのは、その価値があるからです。ここにあるのは、チェックリストから写した一般的な注意ではありません。どれも、2026年11月12日に最初の公開ノードを立てる過程で、私が実際にやった失敗で、どれも本当に時間を溶かしました。あのとき誰かにこう書いておいてほしかった、という書き方をしています。

#1 — I forgot the root password, and I had not written it down.#1 — root パスワードを忘れた。しかも、どこにも書いていなかった。

This is the expensive one. XServer cannot display your root password to you, and cannot reissue it. There is no recovery flow. My only way back was to reinstall the OS and start the entire setup from zero — server, installer, everything. So: ALWAYS record the password, somewhere you will actually keep, before you do anything else. Two habits that would have saved me: use the "show password" (eye) icon on the setup form and visually confirm what you typed before submitting; and choose a password made only of lowercase letters and digits — phone keyboards auto-capitalise the first letter, and a password you cannot type reliably into a serial console is a password you do not really have.これが一番高くついた失敗です。XServer は root パスワードを表示できませんし、再発行もできません。復旧フローは存在しません。私の戻り道は、OS を再インストールして、サーバーもインストーラーも全部最初からやり直すことだけでした。だから：他の何をするよりも先に、パスワードを必ず、確実に残る場所へ記録してください。私を救ったはずの習慣が2つあります：設定フォームの「パスワードを表示」（目のアイコン）で、送信前に自分の入力を目で確認すること。そして、パスワードは小文字と数字だけで作ること — スマホのキーボードは先頭を勝手に大文字化します。シリアルコンソールで確実に打てないパスワードは、持っていないのと同じです。

#2 — The serial console kept "eating" my login.#2 — シリアルコンソールにログインを「食べられた」。

The VPS serial console's login prompt times out after about 60 seconds and silently resets — if you are slow (say, typing a password carefully on a phone), the prompt you were typing into is already gone, and your password lands nowhere. It looks like the password is wrong; it usually isn't. Just type it again, calmly. Related phone trap: on a phone browser, switching the console to "desktop view" reloads the console screen and the display clears. That clearing does NOT stop anything on the server — my install kept running fine behind the blank screen. Do not panic, and above all do not restart or re-run anything while an install is in progress just because the screen went empty. VPS のシリアルコンソールは、ログインプロンプトが約60秒でタイムアウトして、静かにリセットされます。入力が遅い（スマホでパスワードを慎重に打っている、など）と、打っていた先のプロンプトは既に消えていて、パスワードはどこにも届きません。パスワードが間違っているように見えますが、大抵は違います。落ち着いて、もう一度打てばいいだけです。スマホ特有の罠もありました：スマホのブラウザでコンソールを「PC版表示」に切り替えると、コンソール画面が再読み込みされて表示が消えます。その消去は、サーバー側の作業を何も止めません — 私のインストールは、真っ白な画面の裏で問題なく進んでいました。慌てないでください。そして何より、画面が空になったからといって、インストールの最中に再起動したり再実行したりしないでください。

#3 — I checked the wrong address, and I listed my node in the wrong shape.#3 — 確認する場所を間違え、ノードの載せ方も間違えた。

Two small traps, one lesson: the node was fine; my checks were wrong. First, opening the node's root URL (/) shows a web page, not a health answer — liveness lives at /api/instances (and /api/health). I spent time "confirming" a healthy node was broken because I was reading the wrong path. Second, when a node is listed in a nodes.json-style registry, each entry must be an object with a url field — {"url": "https://…"}. I first wrote plain URL strings, and every app silently skipped my node: no error anywhere, it just never connected. If your node seems invisible, check the shape of the entry before you check anything else. 小さな罠が2つ、教訓は1つ：ノードは正常で、私の確認方法が間違っていました。1つ目、ノードのルート URL（/）を開くと Web ページが出るだけで、死活の答えは返りません。死活は /api/instances（と /api/health）にあります。私は間違った場所を見て、正常なノードが壊れていると「確認」するのに時間を使いました。2つ目、nodes.json 形式の一覧にノードを載せるとき、各エントリは url フィールドを持つオブジェクト — {"url": "https://…"} — でなければなりません。私は最初、URL の文字列だけを書いてしまい、すべてのアプリが私のノードを静かにスキップしました。どこにもエラーは出ず、ただ接続されませんでした。ノードが見えない気がしたら、他の何より先に、エントリの形を確認してください。

#4 — My node served timelines for hours and delivered nothing.#4 — 何時間もタイムラインは出るのに、1件も届かなかった。

I finished the install, the timeline loaded, and I assumed posting worked too. It didn't: the installer ships VALIDATOR_PRIVATE_KEY empty on purpose, so my node could read and serve but had no wallet to submit anything with. Nothing told me so — reads succeeding feels like "it works". The validator-wallet step (setup step 4) is a required step, not an optional extra. If your node serves but never delivers, check whether the wallet step was actually done and whether the address holds any Base ETH. インストールを終え、タイムラインが表示されたので、投稿も届いているものと思い込みました。届いていませんでした：インストーラーは VALIDATOR_PRIVATE_KEY を意図的に空で出荷するので、私のノードは読む・渡すことはできても、提出するためのウォレットが無かったのです。誰もそう教えてはくれません — 読み取りが成功すると「動いている」ように感じるからです。バリデータウォレットの手順（セットアップのステップ4）は、任意の追加ではなく必須の手順です。ノードが表示はするのに届けないときは、ウォレットの手順を本当に済ませたか、そのアドレスに Base ETH が入っているかを確認してください。

#5 — My node's public address changed underneath me.#5 — ノードの公開アドレスが、いつの間にか変わっていた。

The free Cloudflare quick tunnel is a temporary address. When my tunnel restarted, the URL changed — and anything still pointing at the old URL was pointing at nothing. The node does re-announce itself to the registry automatically, and the current address is always written in /opt/caw/node-url.txt, but a quick-tunnel URL is not a permanent address and must never be treated as one. If people suddenly can't reach your node after a restart, compare the URL they are using with the one in that file before debugging anything deeper. 無料の Cloudflare クイックトンネルは、仮のアドレスです。私のトンネルが再起動したとき、URL が変わっていて、古い URL を指していたものは全部、虚空を指していました。ノードは一覧へ自動で知らせ直しますし、現行アドレスは常に /opt/caw/node-url.txt に書かれますが、クイックトンネルの URL は恒久的なアドレスではなく、そう扱ってはいけません。再起動のあと急にノードへ届かなくなったら、深い調査の前に、相手が使っている URL とそのファイルの中身が一致しているかを見てください。

#6 — Posts stopped, and the fix was embarrassingly simple.#6 — 投稿が止まった。直し方は、拍子抜けするほど単純だった。

My first real stall: a post sat in the queue as processing and nothing moved. I was preparing database surgery when I tried the boring thing first — systemctl restart caw-node — and the stuck post was delivered within a minute. Since then it is always my first move, and it has worked every time so far: the validator seems to deliver once after a restart and then, occasionally, wedge again on the next post. Restarting is cheap and safe; rooting around in the queue database is neither. Only if a restart does not clear it do I look at the queue rows and the logs — and for the one failure a restart cannot fix (a failed row holding a cawonce hostage), that is exactly what caw-doctor unblock was built for. 初めての本物の詰まり：投稿が待ち行列で processing のまま、微動だにしませんでした。データベース手術の準備をしていた私が、先に退屈な方 — systemctl restart caw-node — を試したら、詰まっていた投稿は1分以内に届きました。それ以来、再起動は常に私の初手で、今のところ毎回効いています：バリデータは再起動後に1件届けて、その次で時々また固まる、という挙動のようです。再起動は安くて安全ですが、待ち行列のデータベースをいじるのは、そのどちらでもありません。再起動で解けないときだけ、行とログを見ます — そして再起動では直らない1つの失敗（failed 行が cawonce を人質に取る型）のためにこそ、caw-doctor unblock があります。

7. The honest limits7. 正直な限界

  • One node is one point of failure — for its own users. If your node is the only one someone connects to, your downtime is their downtime. That is the whole reason more nodes matter, and no guide can engineer it away.ノード1台は、単一障害点です — その利用者にとっては。あなたのノードにしかつないでいない人にとって、あなたの停止はその人の停止です。ノードの数が要る理由そのもので、ガイドでどうにかなる話ではありません。
  • Cross-chain movement depends on LayerZero. Names, deposits and archive replication travel between Ethereum, Base and Arbitrum over LayerZero messaging. If that network stalls, posts still land on Base, but cross-chain sync waits. This is a property of the protocol design, not of your server.チェーン間の移動は LayerZero に依存します。名前、預け入れ、アーカイブの複製は、Ethereum・Base・Arbitrum の間を LayerZero のメッセージが運びます。そのネットワークが詰まれば、投稿は Base に届いても、チェーン間の同期は待ちます。これはあなたのサーバーの問題ではなく、プロトコルの設計の性質です。
  • The contracts are immutable and unmodified. Everything on this page — the installer, caw-doctor, this guide — lives in the client and operations layer. The deployed contracts are the original published code, byte for byte; no tool here can change them, and if a contract-level problem is ever found, it cannot be patched in place. Set your expectations accordingly.コントラクトは不変で、無改変です。このページのもの — インストーラー、caw-doctor、このガイド — はすべて、クライアントと運用の層にあります。デプロイ済みのコントラクトは公開された原典コードそのままで、ここにある道具では変更できませんし、コントラクト層の問題が見つかっても、その場で直すことはできません。期待値を、それに合わせて持ってください。
  • Public RPCs are a free lunch with free-lunch service. The default setup reads the chains through public RPC endpoints; they can be slow or rate-limited, and the first sync feels it most. If your node grows popular, pointing it at your own RPC endpoints is the first upgrade to make.公開 RPC は、無料ランチなりの品質です。既定の設定は公開 RPC 経由でチェーンを読みます。遅かったり制限されたりすることがあり、初回同期で一番効きます。ノードの利用が増えたら、自分の RPC に向けるのが最初のアップグレードです。
